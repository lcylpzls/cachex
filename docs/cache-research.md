# 内存缓存设计调研手册

> 调研日期:2026-08-09 · 范围:操作系统缓存 / Go 缓存库 / 分布式缓存 / Redis
> 目的:只取设计思想,代码全部自研。

## 1. 操作系统与硬件缓存

### 1.1 CPU Cache / Linux Page Cache

**设计思想**

- 以「最近访问」为核心:时间局部性(刚访问的数据很快再访问)
  与空间局部性(相邻数据一起加载);
- 容量有限时按替换策略淘汰:LRU 是最直观的近似;
- 缓存命中率决定性能,淘汰策略的选择比数据结构本身更影响效果。

**取其精华**:LRU 作为默认淘汰策略的心智模型;命中率指标是缓存健康的根本。

**去其糟粕**:硬件缓存的分层与伪 LRU 复杂度远超应用层需要,应用层 LRU 已足够。

## 2. Go 生态

### 2.1 groupcache(Brad Fitzpatrick)

**设计思想**

- **Singleflight**:同一 key 的并发未命中只执行一次回源加载,
  其余请求等待共享结果——缓存击穿防护的标杆;
- 一致性哈希:多节点分布式缓存归属;
- 只读缓存:没有 Delete/Update API,强制不可变语义。

**取其精华**:Singleflight 合并回源;Loader 回源模式(GetOrSet)。

**去其糟粕**:只读语义对业务不友好(业务缓存需要失效/更新);
一致性哈希属于分布式范畴,单机库不做。

### 2.2 bigcache(Mail.Ru)

**设计思想**

- **并发分片(Shards)**:默认 16 个 shard,每 shard 独立锁,
  把全局锁竞争摊薄;
- 字节存储:value 以 []byte 存储,避免存 interface{} 的 GC 压力;
- 无 LRU:按写入时间戳淘汰(队列式),省去链表维护成本;
- 定期清理 + 惰性过期双通道。

**取其精华**:分片锁;惰性过期 + 定期清理双通道。

**去其糟粕**:字节存储牺牲类型便利(业务层每次要反序列化);
无 LRU 导致"热数据可能被冷数据挤掉",业务场景不如 LRU 直观。

### 2.3 freecache

**设计思想**

- 环形缓冲区(ring buffer)统一存放 value,零散分配少、GC 压力小;
- segment 分片 + LRU 近似(基于访问计数)。

**取其精华**:分片 + LRU 组合;内存占用可控。

**去其糟粕**:环形缓冲区实现复杂(指针/覆盖管理),对多数业务收益不明显;
value 存储仍以 []byte 为主。

### 2.4 ristretto(Dgraph)

**设计思想**

- **TinyLFU**:准入过滤(新条目先经频率估计器决定是否值得入缓存)+
  SAMPLED LFU 淘汰,兼顾命中率与扫描抵抗(scan resistance);
- Cost 模型:每条目可声明成本,容量按成本而非条数;
- Txn 缓冲:写入先入事务缓冲,异步提交到主结构。

**取其精华**:扫描抵抗思想(一次性批量数据不应挤掉热点);
成本模型(大对象占更多容量)。

**去其糟粕**:TinyLFU/频率估计器实现与调参复杂度高,
对「薄而克制」的定位过重;异步提交引入短暂不一致窗口。

### 2.5 go-cache(patrickmn)

**设计思想**

- 全局 map + RWMutex,简单可靠;
- 每条目独立 TTL(默认 5 分钟),Janitor 后台周期清理;
- Get/Set/Add/Replace/Increment 全 API。

**取其精华**:每条目 TTL + Janitor 清理的心智模型简单实用。

**去其糟粕**:全局锁在高并发下竞争激烈;全 API 面偏大
(Increment/Add 语义边界模糊)。

## 3. 分布式缓存

### 3.1 Redis maxmemory-policy

**设计思想**

- 多种淘汰策略:noeviction / allkeys-lru / volatile-lru /
  allkeys-lfu / volatile-ttl / random;
- 逐出是同步的:写操作触发容量检查,逐出后再写入。

**取其精华**:「写入时检查容量、超限逐出」的触发时机;
TTL 与容量两个正交维度。

**去其糟粕**:LRU 近似(采样)是分布式场景的妥协,单机精确 LRU 更优。

## 4. 设计思想汇总(精华清单)

### 4.1 并发

- 分片锁(默认 16 shard),避免全局锁竞争;
- 命中路径也要写锁(LRU 更新),分片是主要优化手段。

### 4.2 淘汰与过期

- LRU 淘汰(双向链表 + map),容量超限逐出最久未用条目;
- 每条目独立 TTL;惰性过期(读时判断)+ 后台定期清理双通道;
- 逐出回调,便于外部联动。

### 4.3 击穿防护

- Singleflight:同 key 并发未命中合并为一次回源;
- Loader 失败不缓存、不污染,等待者共享错误。

### 4.4 可观测

- 命中/未命中/逐出/过期计数;
- 容量与长度快照;指标外部注入,默认 no-op。

## 5. 明确不采纳的糟粕

- bigcache/freecache 的字节存储(牺牲类型便利);
- ristretto 的 TinyLFU 与异步 Txn(复杂度/一致性代价高);
- groupcache 的只读语义(业务需要更新与失效);
- go-cache 的全局锁与过大 API 面;
- Redis 的采样近似 LRU(单机可做精确 LRU)。

## 6. 对 cachex 的设计映射

| 精华思想 | cachex 落点 |
| --- | --- |
| 分片锁 | `WithShards`(默认 16),每 shard 独立 mutex |
| LRU 淘汰 | 每 shard 双向链表 + map,超限逐出尾部 |
| 每条目 TTL | `SetTTL` + 惰性过期 |
| 定期清理 | `WithCleanupInterval` + `Cleanup()` + `Close()` |
| Singleflight | `GetOrSet` 回源合并,ctx 取消感知 |
| 逐出回调 | `WithOnEvicted`,reason 区分容量/过期 |
| 命中率观测 | `Stats` + Metrics 注入 |
| 类型便利 | value 为 `any`,保持业务零拷贝 |
| 容量模型 | `WithCapacity` 条目上限,成本模型不引入 |

> 本手册为 cachex 设计输入,不构成对外承诺;实现时按需取舍。
